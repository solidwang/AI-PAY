Pay-Core 后端架构方案

三种 Spring Boot 项目结构方案，选择最适合你的

A

单模块分层架构（快速）

单个 Spring Boot 应用，按层+功能包组织

ai-pay/
  src/main/java/com/aipay/
    controller/  ← REST API
    service/    ← 业务逻辑
    mapper/    ← MyBatis-Plus
    domain/    ← 实体模型
    channel/   ← 微信/支付宝
    config/    ← 配置类

优点

  • 启动最快，最少配置
  • 单 pom.xml
  • 适合单人开发

缺点

  • 渠道代码与核心混在一起
  • 不易扩展新支付渠道
B

多模块 Maven（推荐 ★）

单一可部署 JAR，内部按职责拆分 Maven 模块

ai-pay/
  pay-common/  ← DTO、枚举、工具
  pay-core/    ← 订单/退款/账户核心
  pay-channel/  ← 渠道抽象接口
    ├─ wechat/  ← 微信 JSAPI+H5
    └─ alipay/  ← 支付宝手机网站
  pay-api/     ← REST API + OpenSpec
  pay-admin-api/← 后台管理 API
  pay-bootstrap/← 启动入口

优点

  • 渠道可独立扩展，加新渠道不动核心
  • 模块边界清晰，适合后续团队协作
  • 单一 JAR 部署，运维不变

缺点

  • 初始 pom 配置多一些
C

DDD 六边形架构（严格）

领域驱动设计，端口+适配器，框架无关的核心域

ai-pay/
  domain/      ← 纯 Java 领域模型
    aggregate/  ← Order, Refund 聚合
    port/      ← 接口定义（入/出）
  application/  ← 应用服务/用例
  infrastructure/← DB/Redis/渠道适配
  interfaces/   ← HTTP/API 适配

优点

  • 架构最纯粹
  • 核心域完全可测

缺点

  • 前期工程量大 2-3 倍
  • 与 MyBatis-Plus 整合摩擦多
  • 当前阶段过度设计
推荐方案 B：多模块 Maven 是支付系统的工业标准做法，模块边界对应业务边界，新增渠道（如银联、Apple Pay）时不需要动核心代码，同时保持单 JAR 部署的运维简单性。
